CarWifi · 安卓车载 WiFi 与智能消息转发 App

将安卓手机变为车载热点，并在充电 / 低电量 / 短信 / 未接来电等事件触发时，把关键信息自动推送到 Bark、Server 酱、企业微信等自定义渠道。

技术栈推荐：原生 Kotlin + Jetpack 最低兼容：Android 8.0 (API 26) 热点方案：Shizuku / Root（红线） 可行性等级：中高（受系统限制）

核心价值：手机插上车充即自动开热点，让平板、行车记录仪、乘客设备联网；同时手机被「收在车里 / 没带在身上」时，重要短信和未接来电仍能通过第三方推送（Bark 等）实时到达你的主力设备（另一台手机 / 电脑），低电量也能提前报警防止「失联」。

典型使用场景

  • 自驾长途：手机插点烟器车充 → 自动开热点 → 副驾平板、儿童设备联网。
  • 手机放车里充电：本人下车但车里留手机 → 收到验证码短信 → 自动转发到 Bark/企微 → 在主力手机上看到。
  • 低电量守护：电量低于 20% → 推送「手机电量 18%，请尽快充电」到所有已配置渠道。
  • 未接来电不漏接：搭载 NotificationListener 捕获「未接来电」系统通知 → 推送来电号码与时间。

2系统架构

整体采用「常驻前台服务 + 事件接收器 + 统一消息调度器」结构。所有外部触发事件先汇聚到 CoreService，再分发给两个能力模块：TetheringController（热点）与 MessageDispatcher（消息转发）。

架构原则：① 所有事件先入 CoreService 做去重 / 节流 / 状态判定；② 热点与消息两条能力线解耦，互不影响；③ 渠道通过接口抽象，新增渠道只加一个实现类。

3四大功能模块技术实现

① 车载 WiFi（充电自动开 / 关热点）

监听 ACTION_POWER_CONNECTED / ACTION_POWER_DISCONNECTED，命中后调用热点控制器。

🔴 红线（Android 10+ 最关键的系统限制） 普通应用无法通过公开 API 直接开启热点。Android 8 的 WifiManager.setWifiApEnabled() 是隐藏 API，Android 10 起彻底移除；官方 TetheringManager.startTethering() 标注 @SystemApi，仅系统 / 设备所有者可用。因此「自动开热点」必须走以下路径之一：
方案原理用户成本推荐度
Shizuku通过 ADB 授权（无线调试 / 电脑一次授权）桥接，调用隐藏 API 开启热点，无需 Root首次需开「无线调试」配对一次推荐
Root直接以 root 身份调用隐藏 API / su 命令需已 Root 设备备选
Device Owner / MDM企业部署，DevicePolicyManager 放行 tethering需刷机/企业环境特殊
跳转设置页（ACTION_TETHER_SETTINGS）仅弹到热点开关页，仍需用户手动点无法真正自动不自动

结论：MVP 以 Shizuku 为默认路径，App 内引导用户完成一次无线调试配对；检测到 Shizuku 不可用时降级为「弹通知提醒手动开热点」。

② 短信转发

  • 注册 RECEIVE_SMS 广播接收器，在 onReceive 中取出发件人、正文、时间。
  • Android 12+ 下 RECEIVE_SMS 仍可接收新短信广播（无需设为默认短信 App）；若需读历史则必须 READ_SMS（受限，建议仅转发「新到短信」，避开读历史）。
  • 触发 MessageDispatcher.send(AlertMessage(type=SMS, ...))。

③ 未接来电转发

  • 方案 A（推荐）：NotificationListenerService 监听系统「未接来电」通知，提取号码与时间，稳定且无需 READ_CALL_LOG 敏感权限。
  • 方案 B：READ_PHONE_STATE 捕获 CALL_STATE_RINGING → IDLE，再查 READ_CALL_LOG 判定是否未接。权限更敏感、更易被系统回收。

④ 低电量提醒

  • 前台服务内注册 ACTION_BATTERY_CHANGED 或用 BatteryManager 轮询；用户设阈值 N%（默认 20%）。
  • 采用边沿触发 + 去抖：仅在「电量首次跌破 N%」时发一次，充电回升到 N%+ 后重置标志，避免循环刷屏。
  • 复用 MessageDispatcher，与短信 / 来电走同一套渠道配置。

4统一消息调度器（MessageDispatcher）

这是 App 的「复用核心」。所有事件（短信 / 来电 / 低电量）都转换为统一的 AlertMessage，经模板渲染后由对应 Channel 实现发送。支持：自定义渠道、占位符模板、失败重试、离线队列。

渠道请求方式端点示例关键字段

或自建 https://<server>/push		 title, body, level, sound
Server 酱 GET / POST https://sctapi.ftqq.com/SCT<KEY>.send title, desp（支持 Markdown）
企业微信机器人 POST JSON https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<KEY> msgtype:text, content
自定义 Webhook 用户定义 任意 URL 方法 / 请求头 / Body 模板（{{sender}} 等占位符）

模板占位符（所有渠道通用）：{{event}} 事件类型 · {{sender}} 发件人/号码 · {{body}} 内容 · {{time}} 时间 · {{battery}} 电量 · {{device}} 设备名。

关键代码示例（Kotlin）

// 统一消息模型
data class AlertMessage(
    val type: AlertType,        // SMS / MISSED_CALL / LOW_BATTERY
    val sender: String,
    val body: String,
    val battery: Int? = null,
    val timestamp: Long = System.currentTimeMillis()
)

// 渠道抽象：新增渠道只需实现此接口
interface Channel {
    val id: String
    suspend fun send(msg: AlertMessage, template: String): Result<Unit>
}

class BarkChannel(private val baseUrl: String, private val key: String) : Channel {
    override val id = "bark"
    override suspend fun send(msg: AlertMessage, template: String): Result<Unit> {
        val text = render(template, msg)
        val url = "$baseUrl/push"
        val json = """{"title":"${msg.type}","body":"$text","device_key":"$key"}"""
        return runCatching { httpPost(url, json) }   // 内部含重试 + 超时
    }
}

// 调度器：并发发往所有已启用渠道，带重试与去抖
class MessageDispatcher(private val channels: List<Channel>) {
    suspend fun dispatch(msg: AlertMessage) {
        channels.filter { it.enabled }.forEach { ch ->
            retry(times = 3, backoff = 2000) { ch.send(msg, ch.template) }
        }
    }
}

6可行性红区、风险与合规

🚫 不可绕过的硬限制 ① 非 Root / 非 Shizuku 下无法自动开热点——这是设计最大前提，必须向用户明示；② Android 后台短信/通话监听在省电策略下可能被延迟，实时性不保证 100%；③ Google Play 对「读取短信/通话记录」类应用审核极严，建议以 GitHub / 官网分发（侧载）为主，不上架 Play 或仅作为「工具类」走特殊声明。
✅ 合规与隐私建议（降低风险）
  • 所有渠道配置（token / key）仅存本地 DataStore，不回传任何服务器。
  • 转发内容可开启「仅转发号码 / 隐藏短信正文」开关，降低隐私泄露面。
  • 首次使用弹出明确告知：本 App 会读取短信与来电并转发到用户自配渠道。
  • 提供「转发日志」本地审计页，用户可随时查看发了什么、发到哪。

8工程构建与侧载部署

本仓库即完整 Kotlin 工程（carwifi-android-design/），可直接用 Android Studio 打开。结构：

路径内容
app/build.gradle.kts依赖：Compose / DataStore / Shizuku / 协程
app/src/main/java/com/carwifi/app/core(服务) · receivers · listener · tethering · dispatch · data · ui · shizuku · util
AndroidManifest.xml权限 + 四大组件声明 + Shizuku provider

前置条件

  • 开发机：Android Studio（含 JDK 17）、compileSdk 34 对应 SDK 平台。
  • 目标设备：Android 8.0+；要实现「自动开热点」需安装并运行 Shizuku App（或已 Root）。
  • 首次构建需联网下载 Gradle 依赖（Compose BOM、Shizuku 等）。仓库未带 Gradle wrapper，可用 Android Studio 打开时自动生成，或本地执行 gradle wrapper。

Shizuku 配对（自动开热点必需）

  1. 设备：设置 → 关于手机 → 连点「版本号」开启开发者选项 → 进入「无线调试」并开启。
  2. 打开 Shizuku App → 通过「无线调试」启动 Shizuku 服务（首次需输入配对码）。
  3. 打开本 App → 设置页「Shizuku 授权」→ 点「请求授权」→ 在 Shizuku 弹窗中允许。
  4. 授权成功后状态变「已授权」，插车充即自动开热点。

构建 / 运行

  • Android Studio 打开 carwifi-android-design → Sync Project → Run 到已连接设备。

侧载分发（自用 / 给朋友）

  • Build → Generate Signed Bundle / APK → 自签 keystore（妥善保管）。
  • 产出 app-release.apk，通过 adb install 或文件分享安装。
  • 首次打开请依次完成：授予短信/电话/通知权限 → 关闭电池优化 → 开启「通知使用权」（未接来电）→ Shizuku 授权。
⚠ 分发须知 因使用 RECEIVE_SMS / READ_CALL_LOG 等权限，不建议上架 Google Play（审核极严且易拒）。侧载模式下这些权限可直接授予，功能完整。分发给朋友时请一并说明上述授权步骤。

9结论与下一步

该产品在技术上天花板清晰、可行：消息转发（短信 / 来电 / 低电量）用公开 API + 前台服务即可稳定实现；唯独「自动开热点」受 Android 10+ 系统限制，必须以 Shizuku（或 Root）为前提——这是设计的第一约束，已在上文用红线标出。

下一步可由你选择：① 直接产出完整 Kotlin 工程脚手架（含上述 4 模块源码）；② 先实现某一核心模块（如 MessageDispatcher + 渠道）；③ 仅保留本设计文档作为立项依据。我可继续推进。
